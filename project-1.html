Incursion

Incursion is a third-person shooter roguelike developed in Unreal Engine 5 over 7 months as a third-year project at Falmouth Games Academy. As Project Lead and Programming Lead, I oversaw the development of Incursion and contributed many core systems.

Core Contributions

Weapon Mod Effects System

Incursion is a roguelike with a variety of upgrades the player can equip. For the designers, it was critical that these effects were easy to script and iterate on in Blueprint.

Key to allowing easy creation of upgrades and modifiers was keeping each effect as decoupled as possible. Following the open-closed principle, creating a new effect should not require modifying any other class. To manage this, each modifier extends the abstract UAttackModifier class and implements its only method: Evaluate().

The result is that a modifier can check any conditions it has and modify the reference values passed in without any knowledge of the other modifiers being applied. For instance, a modifier that boosts headshot damage will apply regardless of whether the player landed the headshot naturally or an upgrade converted a bodyshot into a headshot.

Waypoint Guidance System and Editor Tool

To guide the player to their objectives, the team needed a waypoints guidance system they could use to naturally lead the player.

In the editor, it was important that level designers were able to easily create waypoint positions and see how they connected to each other. For this, I utilised Unreal Engine's FComponentVisualizer class to draw the connections for every waypoint reachable from the waypoint selected in the editor. As these connections form a graph, traversing this graph could cause an infinite loop. To avoid this, I store a TSet for visited nodes and a TSet for unvisited nodes. This way, each connection will only be drawn if it has not yet been visualised and each waypoint will only be visited once regardless of loops.

Broadcast/Listener Components and Visualiser

When blueprint actors needed to call methods on another actor, it was important that I keep their classes decoupled. To achieve this, I implemented a system similar to the observer pattern by creating the classes UBroadcastComponent and UListenerComponent. Each UListenerComponent pointed to a blueprint or C++ method on its parent actor and each UBroadcastComponent stored a set of listeners to trigger. This kept the classes of each actor in the level much simpler and more decoupled.

However, keeping track of these connections was not trivial. They only existed in the inspector tab of the UBroadcastComponent. To make tracking these relationships easier, I drew them using UComponentVisualizer. Now, level designers could easily see what listeners were being broadcast to and each arrow was labelled with the actor being broadcast from, the actor being broadcast to and the method that was to be triggered on that actor.
